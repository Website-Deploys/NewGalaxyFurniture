# Local KV state repair to unshadow the verified sofa SKU (review v1)

The admin editor was showing the auto-generated SKU `NGF-SOF-9E2HP8` for the "Premium 3+1+1 Sofa Set" because a stray duplicate product (`p_eg3vtxpioj`, slug `premium-3-1-1-sofa-set`, status REVIEW) lived only in the local, git-ignored `.wrangler/state` KV cache, and the local `index:products` mapped that stray id instead of the verified product (`p_322e7n6mth`, slug `brown-sofa`, SKU `NGF-SOF-WBJZX0`, committed to `data/products/brown-sofa.json`). Since `resolveProduct` is draft-first and index-driven and `ProductForm` has no editable SKU field by design, this was a data-state defect, not a source bug. The fix is a one-off, local-only repair script (`scripts/repair-sofa-kv.ts`) that rebuilds `index:products` from the committed `data/products/*.json` using the codebase's own `ProductSchema` + `summarize()`, and deletes the stray `draft:p_eg3vtxpioj` key. No tracked source file was modified; no product was created or published; nothing was committed.

Watch for: the fix lives entirely in disposable local KV state, so the same stray draft can reappear if a REVIEW-status product without a repo file is ever re-created (**likely**); the repair is a manual, non-repeatable script rather than a general recovery path (**confirmed**); the "smallest safe fix" here is a state repair, not a code change, which is durable only insofar as the repo remains the authority and KV a rebuildable cache (**confirmed**).

**Verdict**: APPROVED

## High-level view

The diagnosis holds up against the code. `resolveProduct` (src/lib/github/drafts.ts) returns the KV `draft:<id>` first, then falls back to the repo file located via the `index:products` slug mapping. With the local index pointing only at the stray id and a `draft:p_eg3vtxpioj` present, the admin list and editor surfaced the auto-generated record — exactly the observed symptom. The verified product's own draft (`draft:p_322e7n6mth`) and committed file were intact the whole time.

The chosen fix respects every user constraint: it never touches `data/products/brown-sofa.json` (id `p_322e7n6mth`, SKU `NGF-SOF-WBJZX0`, price 41990, name and content unchanged), creates no second product, publishes nothing, and commits nothing. The regression test `real-content-sofas.test.ts` pins the SKU, name, price, slug, and the WhatsApp `(SKU: NGF-SOF-WBJZX0)` string, and passes 17/17 — a meaningful anchor that would fail if the verified identity regressed.

The script is repository-authoritative, mirroring `rehydrateFromRepository`, with one deliberate addition: an explicit delete of the stray draft, which a plain rehydrate would not remove because rehydrate only iterates over slugs that have a repo file. It resolves the wrangler entrypoint directly (no shell), hard-refuses any `--remote` argument, and pins every command to `--local`.

The durability question is the one real caveat. This repairs a cache. Because `.wrangler/state` is git-ignored and rebuilt on demand, the fix is correct and appropriate for the reported problem, but it does not prevent the stray from being regenerated, and the script itself is a single-purpose artifact hard-coded to this one id.

Acceptable given KV is a cache, but worth noting that CI cannot regression-guard this specific resolution.

<summary>Details</summary>

### Why a state repair is the right lever

`resolveProduct` reads `draft:<id>` first and only then consults the repo, locating the file through the `index:products` slug mapping (`productSlugFor`). The editor renders whatever record it gets, and `ProductForm` exposes no SKU field, so a "wrong, uneditable" SKU can only mean the resolver returned a different record than the verified one. The stray `p_eg3vtxpioj` had its own draft and was the sole entry in the local index, so it won every lookup that flowed through the list. That matches the symptom precisely, and it explains why no source edit was warranted: the committed `brown-sofa.json` and the `draft:p_322e7n6mth` key were already correct.

### Repository-authoritative rebuild, plus a delete rehydrate can't do

`buildIndexFromRepository()` reads every `data/products/*.json`, validates with the real `ProductSchema`, and projects with the real `summarize()` — the same primitives `rehydrateFromRepository` uses. The important asymmetry with rehydrate is deliberate: `rehydrateFromRepository` iterates over repo slugs and, for each, either restores or deletes the draft for *that product's* id; it has no mechanism to remove a draft whose id has no corresponding repo file. So a plain rehydrate would rebuild the index without `p_eg3vtxpioj` but leave `draft:p_eg3vtxpioj` orphaned. The script's explicit `kv key delete draft:p_eg3vtxpioj` closes that gap. It also guards against the pathological case where the stray somehow gained a repo file (`if (ids.includes('p_eg3vtxpioj')) throw`), aborting rather than silently re-indexing it.

### Non-atomic repair

The `--remote` guard, direct-entrypoint spawn, and `0600` scratch file (removed in a `finally`) are covered in the high-level view. The residual concern the script does not eliminate: the two mutations (index put, then stray delete) are not atomic. A crash between them would leave the index correct but the orphan draft lingering. Because the resolver keys drafts by id and the verified editor uses `p_322e7n6mth`, even that intermediate state resolves the correct record — so the impact is low, but a re-run is the only way to reach the clean end state.

### Constraint conformance

Every hard constraint is independently checkable from the committed tree. `data/products/brown-sofa.json` is unchanged (`git status` shows only untracked `.agents/` and `scripts/repair-sofa-kv.ts`), so id `p_322e7n6mth`, SKU `NGF-SOF-WBJZX0`, name, price 41990, and content are preserved by construction. No `premium-3-1-1-sofa-set.json` exists, so no second product. Nothing is published and nothing is committed. `real-content-sofas.test.ts` (17/17) pins the SKU, name, slug, price, and the WhatsApp `(SKU: NGF-SOF-WBJZX0)` message, covering the WhatsApp-enquiry requirement directly.

### Durability and recurrence

Repairing `.wrangler/state` is the appropriate scope for a defect that exists only there, and the repo-as-authority / KV-as-cache model makes the repair legitimately "the smallest safe fix." The tradeoff is that it fixes an instance, not a class. The stray was an auto-generated REVIEW-status draft with no repo file; whatever workflow produced it (a create/import that wrote a draft + index entry without committing a file) can produce another, and the next one would shadow the verified product again through the same index path. Hardening that — pruning orphan index/draft entries on rehydrate, or having the resolver prefer records that have a repo file — is out of scope for this task but is the durable follow-up.

### Test coverage

Covered: the committed product identity and the assembled WhatsApp message, via `real-content-sofas.test.ts` (17/17). Typecheck clean (`npm run check`: 0 errors). Full suite 969 pass with 5 pre-existing unrelated failures (build-artifact/SEO/showroom) that also fail on the clean base commit, plus one occasionally-flaky auth-lockout timing test that passes in isolation.

Not tested: the KV resolution path itself. Nothing in the automated suite exercises `resolveProduct` against a populated `index:products`, so the specific bug (index shadowing an orphan draft) has no regression guard — its absence was verified only by manual `wrangler kv ... --local` reads, which CI cannot reproduce. That's an inherent limit of fixing local cache state, not a defect in the fix, but it means recurrence would not be caught by tests.
